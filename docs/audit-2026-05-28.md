### 1.1 Overlay / z-index audit (the Part 1 deep-dive)

**Finding: there is no single z-index ladder, and a good modal primitive exists
but is under-used.**

`app/_components/ui/Modal.tsx` is a correct, accessible dialog primitive —
`z-[100]`, `var(--scrim)` backdrop, **focus-trap**, **body-scroll-lock**, **Esc
closes**, focus restore on close. Its own header comment says existing call-sites
"will migrate in their respective phase commits." **That migration is incomplete.**

The z-index values actually in use across the app, today (from a full grep):

| Tier (observed) | Values seen | Examples |
|---|---|---|
| Progress bar | `z-[1000]` | `RouteProgress` |
| Pop-out window | `z-9999` | `PopOutContainer` (Zoom pop-out) |
| `ui/Modal` primitive | `z-[100]` | the *correct* tier |
| High ad-hoc modals | `z-[80]/[81]` | `ContractManagement`, `ConfirmDialog` |
| Mid ad-hoc modals | `z-[60]/[61]` | `ActNowRail` DiveInModal, `BidPrepModal`, `RosterPanel`, `BenchTab` drawer, `AccountPane`, `DeleteProjectModal`, `EngineerSessionClient` escalate, `EngineerIncomingRequest`, `WalletTab`, `CallClient` |
| Legacy modals / drawers / toasts | `z-50` | `DashboardClient` rings, `PaywallModal`, `EngineerProfilePane`, `admin-v2/Drawer`, `StaffShell` toasts, several `RoomClient` modals/sheets |
| Popovers / dropdowns | `z-10`–`z-40` | menus in `RoomClient`, `DashboardClient`, `EngineerPresenceBall`, `MatchingActions`, `EngineerProfilePane` |
| Mobile drawer/sheet | `z-40` scrim / `z-50` panel | `RoomClient` sidebar + chat sheet |

**Consequences:**
- Ad-hoc modals (everything at `z-50`/`z-[60]`/`z-[80]`) have **no focus trap and
  no body-scroll-lock** — keyboard focus can escape behind the dialog and the page
  scrolls under the modal. Only the few call-sites using `ui/Modal` get those.
- Stacking is **accidental**, not designed: a `z-[60]` modal sits under a `z-[80]`
  modal under the `z-[100]` primitive — fine by luck, but two overlays from
  different tiers opening together can mis-stack (this is the class of bug behind
  the originally-reported "scope modal + search layer stacked wrong"; the specific
  scope-modal instance was the D1 AI-panel issue, already fixed).

**Proposed ladder (for sign-off)** — encode as tokens (e.g. CSS vars
`--z-base/--z-dropdown/--z-sticky/--z-drawer/--z-modal/--z-toast/--z-popover-top`)
and replace every arbitrary value:

```
base content      0
dropdown/popover  1000
sticky bars       1010
drawer + scrim    1020
modal + scrim     1030   ← ui/Modal lives here; ALL modals route through it
incoming-call ring1040   ← must sit above an open modal
toast             1050
route progress    1060
zoom pop-out      1070   (separate OS-window-like surface)
```

### 1.2 Customer `/room` 3-column responsive (D4) — overflow criterion MET

The customer room is a 3-column layout (left project rail · main · right chat) with
a draggable resize handle (`RoomClient.tsx:3416`) and mobile drawer/sheet fallbacks
below `md`. The reported defect was horizontal overflow below ~1280.

**Measured, headlessly** (objective — `documentElement.scrollWidth` vs
`clientWidth`), in the live 3-column session view, at every target width:

```
W=768  OVERFLOW=0px ✓  main=508px
W=900  OVERFLOW=0px ✓  main=640px
W=1024 OVERFLOW=0px ✓  main=724px
W=1180 OVERFLOW=0px ✓  main=880px
W=1280 OVERFLOW=0px ✓  main=980px
W=1366 OVERFLOW=0px ✓  main=1066px
W=1440 OVERFLOW=0px ✓  main=1140px
W=1680 OVERFLOW=0px ✓  main=1380px
W=1920 OVERFLOW=0px ✓  main=1620px
```

**No horizontal page scroll at any width.** The pervasive `min-w-0 flex-1` pattern
(from the recent UI pass) lets the main pane shrink gracefully instead of pushing
the page wide. The brief's core acceptance ("no horizontal page scroll at
1366/1440/1680/1920") is **satisfied on current code** — I could not reproduce the
overflow. Probe: `tests/_audit_d4_probe.spec.ts`; screenshots `tests/_audit_d4_*.png`.

**What still needs a human at the screen** (qualitative — can't be judged headless):
whether the rail should auto-collapse to icons in the 768–1180 band (main is
~508–880px there — functional but tight), whether the right chat should become a
toggle rather than always-on, and the resize-handle UX. These are polish calls on a
layout that is *not broken* (no overflow), so I did not blind-edit them.

**D1 fix detail:** the AI section is now collapsed by default behind a
"Review project history (AI)" disclosure and height-bounded (`h-72 overflow-hidden`)
in both modals, so the one-page bid form is the primary content. Re-tested live
(see flow 2.C below): the modal is usable end-to-end.

### 2.A — call request → ring → ops queue → fall-through — **PASS**

**Repro recipe:**
1. Seed a `queued` `guest_calls` row for customer *niraj* + a `client_intakes`
   row linked via `guest_call_id` (exactly the rows the intake wizard creates).
   Make engineer *freya.ivanov* the single available engineer.
2. Call `match_engineer(intake_id)` — the RPC the intake wizard fires on completion.
3. Customer *niraj* loads `/intake/matching/{intakeId}`.
4. Engineer *freya.ivanov* loads `/dashboard`.
5. Ops viewer (*admin@relay.com*, `super_admin`) loads `/supervise`.

**Observed (live):**
- `match_engineer` returned **1 offer** to ivanov (`match_score 0.75`, `status=pending`).
  Matcher logic works (skill/experience scoring + availability + de-dupe).
- **Customer:** the **"Ringing your engineers"** hero rendered (real offer driving it).
- **Engineer:** the **"Incoming match"** ring rendered on `/dashboard`.
- **Ops:** the queued `AUDIT-2A Cust` session appeared on the `/supervise` board.
- **Fall-through (DB-verified against the `list_queue` filter):** while the offer
  was `pending` + unexpired, the call had `livePendingOffers=1` → **hidden** from
  the engineer pull-queue (`list_queue` excludes calls with a live pending offer).
  After expiring the offer, `livePendingOffers=0` and the call was still `queued`
  → it **surfaces** in the pull-queue for any engineer to claim. This is the
  designed fall-through: *ring → (no answer / expire) → pull queue*, not an
  auto-re-ring.

**Findings / boundaries (honest):**
- **Pod supervisors do NOT see unclaimed queued calls.** `/supervise`'s waiting
  queue is scoped to `pod_id = my-pod OR supervisor_user_id = me OR
  reassign_needed`. A brand-new `queued` call has `pod_id=null` /
  `supervisor_user_id=null`, so **only an unscoped/`super_admin` ops viewer sees
  customers who are still ringing**; a pod supervisor only sees the session once
  it's claimed into their pod. If the brief's "supervisor queue" means a *pod*
  supervisor should watch customers waiting, this is a gap (see §3). Verified the
  ops/super_admin path here.
- **Pull-queue ring UI is disabled.** The legacy `EngineerIncomingRequest`
  pull-ring is commented out in `StaffShell` (push-ring `EngineerIncomingMatch`
  is the active path). The `list_queue` RPC + the `/dashboard` queue list still
  back the fall-through, and the filter behavior is verified, but the
  *engineer-claims-from-the-pull-queue* click was not exercised end-to-end here.

   realtime channel + poll; this one is a one-shot fetch. Wire a channel (or poll)
   so the round-trip closes without a manual reload (feeds §4).

### 2.E — presence idle/busy auto-flip — **PASS**

**Mechanism** (`EngineerPresenceBall`): two signals — on-call (realtime on
`guest_calls` where `claimed_by=me` in assigned/joining/live/grace) and idle (no
mouse/key/touch/focus for `IDLE_MS = 5 min`) — combine in `recompute()`:
on-call → **busy**, idle → **offline**, else → **online**, written via
`set_engineer_presence`.

**Observed (live):** engineer *ivanov* on `/dashboard`; I inserted a claimed live
call → the engineer's own browser detected it via realtime and **DB
`presence_state` flipped `offline → busy`**; ending the call flipped it back to
**`online`**. Both transitions verified by polling the DB.

**Boundaries / observations:**
- The **idle → offline** leg uses a 5-minute timer — verified by code, not
  time-tested (a 5-min wait isn't practical in CI).
- `recompute` only fires on a **transition**, not on mount. A fresh `offline`
  engineer who opens the dashboard and does nothing **stays offline** (and is
  therefore not matchable) until they manually "go on duty" or a signal changes.
  This appears intentional (explicit on-duty entry), but flagging it since it
  means presence isn't auto-asserted on page load.

two instances of the same component ever mount simultaneously they'd collide on
the shared name — the suffix pattern used by the per-user channels would be the

## 3. Needs owner decision (config / product gaps — not bugs)

1. **No explicit "Reject" / "Request changes" on the customer bid viewer.** The
   customer's `ContractManagement` BidViewer offers **Accept & pay** and **Ask for
   appointment** only. There is no first-class *decline* or *request-changes*
   action — the customer's only "no" path is to ask for an appointment. Confirm
   whether a decline/counter action is wanted before go-live.
2. **New-bid notification is in-app only.** The customer learns about a new bid
   via the blinking "Contract management" badge when they're on `/room`. There is
   **no email/SMS push** on a new bid. If customers should be notified out-of-band,
   we need: notification channel keys (SendGrid for email — already wired for the
   morning brief; Twilio for SMS — not wired), and a trigger on `submit_project_bid`.
3. **T&C is a placeholder.** `/legal/contracting-terms` is a stub page. Legal must

4. **Should pod supervisors see the unclaimed "ringing" queue?** Today only

## 4. Systemic issues

1. **Overlay components don't all use design tokens / the z-index ladder.**
   `EngineerIncomingMatch` (D2) hard-codes hex colors, an `rgba()` scrim, and a
   bare `z-50`. The Part 1 brief calls for a single documented z-index ladder
   (toast > modal > popover > drawer > base) with every arbitrary z-index replaced
   by a token. A repo-wide grep for raw `z-[` / `z-50` / `rgba(` / `#`-hex in
   overlay components is warranted — this is almost certainly not the only one.
   (Full sweep pending under Part 1.)
2. **A couple of surfaces break the otherwise-consistent realtime pattern.**
   `SessionEscalationFlag` (engineer's view of an escalation's resolution) does a
   one-shot fetch with no channel — so a resolved escalation only reflects after a
   reload (flow 2.D, finding 2). And the supervisor's resolve-note uses
   `window.prompt`. Both are one-offs against an otherwise-solid pattern; worth a
   sweep for other one-shot fetches that should be live.
3. **Realtime + poll belt-and-suspenders is consistent and works.** Both verified
   surfaces (supervisor roster, engineer ring) pair a Supabase realtime channel
   with a short polling fallback, so a dropped event doesn't strand the actor.
   This is a good pattern; the 2.G channel enumeration will confirm it holds
   everywhere (and that channels are cleaned up on unmount).
